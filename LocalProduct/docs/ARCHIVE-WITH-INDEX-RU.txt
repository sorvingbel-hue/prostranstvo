ПРОСТРАНСТВО — БУДУЩАЯ ФУНКЦИЯ «АРХИВ С ИНДЕКСОМ»

Поручение пользователя: добавить в будущий план предложения архивации,
когда заканчивается место. Управление пока через текущий чат, Codex или Дот;
новый интерфейс общения сейчас не разрабатываем. Этот документ — проект
функции, не описание уже работающего архиватора. Реальные файлы не архивируем.

СЦЕНАРИЙ
1. Приложение измеряет свободное место на выбранных дисках локально,
   по отдельно включённому расписанию или нашему запросу. Порог задаётся
   явно в ГиБ/процентах, с повторным порогом снятия и периодом тишины.
2. Из разрешённых папок готовит кандидатов: типы файлов, объём, приблизительная
   выгода, причина выбора, оценка времени/нагрузки и нужного рабочего места.
   Давность изменения — только признак отбора, а не доказательство ненужности.
3. Предложение сохраняет в локальную очередь. При обращении из Codex/Дот
   возвращает готовый отчёт. Локальный stdio MCP сам по себе не запускает
   новую беседу с моделью и не гарантирует push в закрытый чат. Отдельный
   событийный канал/агент можно добавить позже по принятой политике.
4. Мы выбираем конкретный план. Сначала архивируется небольшая тестовая
   папка с сохранением оригиналов. Автоматического удаления исходников нет.
5. После внедрения безопасного освобождения места: потоковая проверка
   распаковки каждого файла по SHA-256, фиксация каталога и только затем
   отдельный явно выбранный этап удаления/замены оригиналов по политике.
   Само создание архива рядом с оригиналами место не освобождает.

ЧТО ПРЕДЛАГАЕМ
- Первые кандидаты — текст, CSV, JSON, логи и исходные тексты в разрешённых
  пользовательских папках. Не включать активные проекты и базы без выбора.
- Не обещать заметное сжатие JPEG/MP4/уже сжатых ZIP/7z, многих PDF/DOCX.
  Оценку получать ограниченным пробным сжатием и показывать погрешность;
  результат не стоит экстраполировать с одного маленького файла на весь диск.
- Сначала проверять, есть ли место для самого нового архива и резервов.
  Если места недостаточно — предложить иной выбранный диск; не начинать
  с удаления оригиналов. Новый архив делать вне исходного дерева отбора.
- Активные Windows-файлы, установленные приложения, облачные placeholders,
  ссылки, секреты, миры игр и незавершённые загрузки по умолчанию исключены.

СЖАТИЕ И ФОРМАТ
Наша ценность — выбор кандидатов, проверка целостности, поиск и восстановление.
Используем проверенное сжатие без потерь. Свой новый математический codec
не нужен для первой версии; замена текста пересказом ИИ архивированием не будет.

Кандидаты для сравнительного испытания на синтетическом наборе:
- ZIP + Deflate/ZIP64: доступен в Python stdlib, понятный переносимый формат.
- 7z/LZMA2: сравнить размер, время, RAM и скорость восстановления одного файла.
  LZMA SDK опубликован в public domain; полный 7-Zip имеет отдельные лицензии.
- Zstandard: открытое сжатие; отдельно выбрать контейнер/индекс и совместимость.
  Лицензия проекта — BSD либо GPLv2 на выбор. Финальный состав и notices
  проверять для фактически включённых версий/файлов при подготовке пакета.
В первой реализации не создавать закрытый формат, читаемый только нами.
Не использовать UnRAR как основу создания RAR-архиватора: у распаковщика
отдельная лицензия с ограничениями. Для исходного исследования достаточно
документации; чужие проприетарные исходники не требуются.

КАТАЛОГ И ПОИСК
- Сохранить стабильный ID документа и использовать выбранный основной
  каталог, расширив его модель хранения. Не создавать молча второй File Atlas.
- Для записи хранить: исходный путь/имя, тип/даты, SHA-256 исходных байтов,
  размер до сжатия, ID/путь/хеш архива, имя элемента, метод сжатия, версию схемы
  и состояние операции. Разделять физический файл и элемент внутри архива.
- Поиск по имени/метаданным находит и архивные элементы. В ответе явно:
  «в архиве …», размер и действие «подготовить восстановление».
- Полнотекстовый индекс — отдельный этап с определёнными поддерживаемыми
  форматами и политикой хранения; не обещать OCR/понимание всех документов.
- Вместе с архивом сохранять открытый manifest/индекс, чтобы при потере
  программы восстановление было возможно. Основной каталог тоже резервировать.
- Восстановление проверяет все пути, хеши, доступное место и коллизии,
  готовит план и не перезаписывает существующий файл без отдельного решения.
  Переезд архива обнаруживать по ID/хешу и не выдавать старый путь за доступный.

НАДЁЖНОСТЬ И ПРОВЕРКИ ПЕРЕД ИСПОЛЬЗОВАНИЕМ
- Побайтовый round trip: текст, кириллица/Unicode, пустые и большие файлы,
  одинаковые имена в разных подпапках, файлы >4 ГиБ/ZIP64.
- Прерывания на каждой границе: создание .partial, закрытие/проверка архива,
  переименование, commit каталога, переход к освобождению места; идемпотентность.
- Нехватка места, блокировка/изменение исходника, повреждённый архив/индекс,
  отсутствие внешнего диска, перенос архива и восстановление на другом ПК.
- Безопасная распаковка: traversal/абсолютные пути, junction/symlink/hardlink,
  дополнительные потоки, дубликаты имён без учёта регистра, лимиты числа
  элементов/распакованного объёма/коэффициента сжатия и отмена операции.
- Согласованность с главным каталогом, обратный поиск и восстановление
  после потери локальной базы по manifest. Журнал не скрывает неполные этапы.
- Измерение CPU/RAM/времени; низкий обычный приоритет, пауза при активной игре
  по отдельно принятому правилу. Большое сжатие не должно блокировать интерфейс.
