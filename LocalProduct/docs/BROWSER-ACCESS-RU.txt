Подготовка браузерного доступа — 18 ноября 2026

Модуль src/browser_access.py по умолчанию инертен. Импорт, inventory_browsers и
build_browser_access_plan не создают каталогов, не запускают процессы, не открывают
окна, не меняют фокус и настройки MCP. Они не читают вкладки, снимки экрана,
историю, cookie, профили или состояние входа пользователя.

Диагностика проверяет только фиксированные варианты расположения исполняемых
файлов Edge, Chrome, Яндекс Браузера и Notion Desktop в стандартных каталогах.
«Не найдено в известных путях» не доказывает, что приложение не установлено.
Проверка существования файла не подтверждает подлинность или работоспособность
программы. Notion Desktop здесь не получает управление: работу с приложениями
нужно реализовывать отдельным адаптером. Dot этот модуль также не подключает.

Фоновый план

build_browser_access_plan('edge', 'https://example.com/') возвращает только план.
Для Edge и Chrome он содержит шаблон официального Playwright MCP:
  transport/type: stdio
  command: playwright-mcp
  args: --headless --browser msedge (либо chrome)
        --user-data-dir <DATA_ROOT>/browser-access/profiles/<browser_id>
        --image-responses omit

Команда playwright-mcp указана как установленный исполняемый файл официального
пакета @playwright/mcp. Модуль не проверяет его установку, не запускает npx и не
устанавливает/обновляет Node.js, пакет MCP или браузеры. После отдельной настройки
нужны запуск сервера клиентом MCP и проверка настоящего соединения. Совместимость
конкретного клиента и установленной версии пакета ещё не проверена.

Профиль — отдельный каталог данных приложения. Это не флаг Playwright --isolated:
план использует свой постоянный user-data-dir. Личные входы браузера недоступны;
в новом профиле потребуется отдельный вход. Каталоги с symlink/junction в цепочке
блокируются. Корень данных берётся из доверенной конфигурации приложения, а не
из запроса пользователя. Профили Edge и Chrome разделены; один профиль не следует
одновременно использовать в нескольких экземплярах.

План явно возвращает:
  runtime_status = planned_not_started
  browser_control = not_connected_until_MCP_started
  session_access = separate_profile_login_required
  existing_session_access = false
  process_started = false, controllable = false

Нет порта, HTTP/SSE-сервера, remote-debugging/CDP, extension-подключения к текущим
сессиям, переноса профилей/cookie, автозапуска или повышенных привилегий. Headless
управление Яндексом отмечено unsupported; экспериментальная совместимость не
выдаётся за официальную поддержку. --image-responses omit ограничивает ответы
с изображениями; этот параметр сам по себе не запрещает будущему клиенту вызвать
инструмент сохранения снимка. Политику будущих инструментов нужно задавать отдельно.

Видимый запуск

launch_visible_browser(browser_id, url, foreground_authorized=False, spawn=None)
имеет отдельную защиту на каждый вызов. Только literal True в
foreground_authorized разрешает запуск. Разрешение не сохраняется в настройках и
не переносится на следующий запрос. Без него результат blocked_focus_window,
а spawn/subprocess.Popen не вызывается. Сейчас настоящий запуск не выполнялся.

Разрешённый вызов использует только найденный известный exe, список аргументов
[exe, --user-data-dir=<отдельный профиль приложения>, https-url], cwd каталога exe
и shell=False. Путь программы и дополнительные флаги не принимаются от запроса.
Допускаются Edge, Chrome и Яндекс; это только открытие отдельного окна/процесса,
без контроллера страниц. Успех spawn означает launch_requested_not_verified:
не подтверждены загрузка страницы, вход, отсутствие диалогов или управление.
Видимый вызов может открыть окно и изменить фокус: пока ребёнок за ПК, его нельзя
вызывать с foreground_authorized=True. Фоновый процесс этой функцией не запускается.

URL принимает только HTTPS с непустым корректным узлом и портом. Userinfo
(логин/пароль в адресе), javascript/file/http, управляющие символы, обратные слеши
и неоднозначные/повреждённые адреса отклоняются до запуска. Эта проверка адреса
не является ограничением сетевых переходов, перенаправлений или содержимого сайта.

Проверка

python -m unittest discover -s LocalProduct/tests -p test_browser_access.py -v

Все проверки запуска используют Mock. Они проверяют блокировку фокуса, аргументы,
stdio, отдельные пути, ошибку spawn и валидацию URL. Настоящие браузеры, процессы
MCP, пользовательские сессии, страницы и GUI в тестах не запускаются. Это проверка
локальных контрактов, а не подтверждение работы браузерного контроллера.
